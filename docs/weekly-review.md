# Interview prep: weekly reviews

## Elevator pitch (1–2 minutes)

"DocIntake automates document intake for personal-injury law firms. A firm uploads PDFs —
medical records, bills, court filings — and the system extracts the text, with OCR for
scans, classifies the document, pulls out case numbers, parties and dates, matches it to the
right case, and files it following the firm's naming and folder rules. Discovery requests
and hearings automatically create deadline alerts. Anything below a confidence threshold
goes to a review queue where a paralegal confirms the pipeline's suggestion.

The backend is FastAPI with Postgres; processing is asynchronous with Celery on RabbitMQ.
I designed it for at-least-once delivery: every stage is idempotent through a status guard
and a compare-and-set update, transient errors are retried with backoff, and permanent
failures are dead-lettered. It's multi-tenant with JWT auth, has structured logs with a
correlation id that follows an upload through every worker, Prometheus metrics and a
Grafana dashboard, 127 tests including integration tests on real Postgres, and CI on
GitHub Actions. Under load it processes about 35 documents per second with four workers,
and the benchmark showed the bottleneck moving to ingestion, which I then addressed with API
replicas."

## Week 1 — Foundations (API, DB, migrations, CI)

**Likely questions**

1. *Why sync SQLAlchemy in an async framework?* — Celery workers are synchronous, so one
   session model serves both. FastAPI runs sync dependencies in a threadpool, which is fine
   for this I/O profile. Async would add concurrency in the API at the cost of two data-access
   stacks; I'd revisit it if the API became the bottleneck under many concurrent slow clients.
2. *How do you test database code?* — Two layers: fast unit tests on SQLite in memory
   (portable types: `Uuid`, JSON→JSONB variant) and integration tests on real Postgres via
   testcontainers, which also run the actual Alembic migrations and compare them to the
   models (a model change without a migration fails CI).
3. *What did you have to fix in autogenerated migrations?* — Postgres ENUM types shared by
   two tables: each `create_table` tried to create the type again. I create the ENUMs once,
   explicitly, with `create_type=False` on the columns, and drop them in `downgrade`.

**Trade-offs**: SQLite unit tests (speed) vs Postgres-only (fidelity) → both, layered.
Migrations in a one-shot service vs at API startup → one-shot, so replicas don't race.

## Week 2 — Async processing and reliability

**Likely questions**

1. *What happens if a worker dies mid-task?* — `acks_late` means the message is only
   acknowledged after the task finishes, so RabbitMQ redelivers it. The redelivered task is
   safe because stages are idempotent: it checks the document's status and writes with
   `UPDATE … WHERE status = :expected`; if someone already did it, it's a no-op.
2. *Retry vs dead-letter?* — Only transient errors (DB/broker connectivity, timeouts) are
   retried, with exponential backoff and jitter. A corrupt PDF won't get better, so it fails
   immediately: the document is marked `failed` with a sanitized error and the message is
   rejected into the DLQ. A human can retry from the UI after fixing the cause.
3. *A bug you found only with real infrastructure?* — Two. Celery only declares queues it
   consumes, so the DLQ didn't exist and RabbitMQ silently dropped dead letters; I declare it
   on `worker_ready`. And `correlation_id` is an AMQP property Celery fills with the task id,
   so my tracing header was being shadowed; I renamed it.

**Trade-offs**: Celery+RabbitMQ vs Redis/BackgroundTasks/Temporal (ADR 0001). State in
Postgres vs a Celery result backend → Postgres, messages carry only ids.

## Week 3 — Intelligence and product

**Likely questions**

1. *How do you decide when to auto-file?* — Two confidences: classification (max class
   probability) and matching (exact case number = 1.0, otherwise weighted fuzzy name
   similarity + defendant + incident date). Below thresholds, or when the top two candidate
   cases are within 0.05, it goes to review. On synthetic data: 93% auto-filed, 100% of
   those to the correct case.
2. *Why not an LLM?* — Offline, deterministic, cheap, testable in CI and no PHI leaving the
   system. The classifier sits behind a protocol, so an LLM implementation is a drop-in
   (ADR 0002). On real messy documents an LLM would likely win on accuracy.
3. *A bug your tests caught?* — The end-to-end benchmark showed that adding the incident
   date to a strong client-name match *lowered* the score. I wrote a regression test
   ("more evidence never lowers the score") and fixed the formula; auto-filing went from 88%
   to 93% with precision unchanged.

**Trade-offs**: regex entity extraction (explainable, cheap) vs NER models. Rules as
validated JSON per firm (safe, editable) vs code.

## Week 4 — Production readiness

**Likely questions**

1. *How is tenant isolation enforced?* — The firm comes only from the authenticated user;
   the token's `firm_id` must match the user's row on every request; every repository query
   takes `firm_id`; cross-tenant ids return 404. Next step would be Postgres Row-Level
   Security as defence in depth (ADR 0003).
2. *How do you trace one document?* — A correlation id from `X-Correlation-ID` (or
   generated) is bound to structlog's context, copied into Celery message headers on
   publish and restored on `task_prerun`; every log line, API and worker, carries it.
   Sensitive keys are redacted by a log processor.
3. *What did the benchmark teach you?* — Scaling workers 1→4 gave 2.5×, not 4×. Processing
   finished seconds after the last upload: the single API process had become the
   bottleneck. In production the API runs as replicas behind nginx; Prometheus finds
   replicas via DNS. Prefork workers needed prometheus_client's multiprocess mode.

**Trade-offs**: API replicas vs uvicorn `--workers` (replicas keep metrics simple).
Row-level scoping vs schema/database per tenant.
